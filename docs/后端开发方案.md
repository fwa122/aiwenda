实施中因环境（Windows + Node 22.13）额外落定的工程决策：

| 决策 | 原因 |
| --- | --- |
| TypeScript 锁 **5.9**（不用 7） | TS7 移除 `baseUrl` 与 `moduleResolution: node`，Prisma/Nest 生态未适配 |
| Prisma 锁 **6.x**（不用 7） | Prisma7 强制 `prisma.config.ts` + adapter，schema 内不再支持 `url` |
| 构建用 **`tsc -p tsconfig.build.json`**（不用 `nest build`） | Nest CLI 在 Node 22.13 触发 `@angular-devkit`/ora 的 ESM/CJS 循环加载崩溃 |
| 数据库连接串用 **`127.0.0.1`**（不用 `localhost`） | Windows 下 `localhost` 解析为 IPv6 `::1`，连不上 Docker 端口映射 |
| `PrismaService` **懒连接**（去掉 onModuleInit `$connect`） | 避免启动期连接失败阻塞整个应用 |
| service 注入 Prisma 用 **`@Inject(PrismaService)`** | `emitDecoratorMetadata` 将继承 `PrismaClient` 的子类反射为基类，DI token 失配 |
| JWT 守卫链 | `PassportModule.register({ defaultStrategy: 'jwt' })` + AuthModule **再导出 PassportModule**（v12 无 `forRoot()`，且被使用方实例化时需要 `AuthModuleOptions`） |
| 响应拦截器内 **BigInt/Date 安全序列化** | Prisma `BigInt` 字段无法 `JSON.stringify`（递归转换，Date/Buffer 原样放行） |
| 模型路由用**模型名前缀注册表**（不用 per-请求 provider 字段） | 新增 Provider 零协议改动；未识别模型自动回落默认，前后端无感 |
| 内部接口鉴权 **fail-closed** | 令牌未配置返回 503 而非放行，部署遗漏立即暴露 |
| Celery 重试区分 **ValueError vs 其他异常** | 确定性错误（非法路径/空切片）立即永久失败，避免指数退避空转 |

## 一、目标与边界

### 1.1 本阶段目标

把前端已实现的 38 个接口从 Mock 切换为真实服务，交付一条完整可用的 RAG 链路：

```
上传文档 → 解析切片 → 向量化入库 → 提问 → 混合检索 → Rerank → LLM 流式生成 → 引用溯源
```

### 1.2 边界约定

| 项 | 归属 | 说明 |
| --- | --- | --- |
| 用户/会话/知识库/文档元数据 | **Node BFF** | 事务型 CRUD |
| 文件存储与任务编排 | **Node BFF** | 写 MinIO，投递解析任务 |
| 解析、切片、Embedding、检索、Rerank、LLM | **Python AI 服务** | 计算密集 |
| 向量数据 | **向量库** | 由 Python 服务独写独读 |
| 前端 | 保持现状 | 仅切换 `VITE_USE_MOCK=false` |

> **重要原则**：Node 不直接操作向量库，Python 不直接对外暴露。两侧通过 PostgreSQL 共享状态、通过 HTTP 内部接口通信。

## 二、技术选型分析

### 2.1 Node 框架

| 方案 | 优势 | 劣势 | 适用 |
| --- | --- | --- | --- |
| **NestJS** | 模块化、依赖注入、装饰器路由、内置 Swagger/校验/拦截器；38 个接口规模下结构最清晰 | 概念多、上手成本高 | ✅ **推荐**（本项目接口多、需长期维护） |
| Express + 手动分层 | 极简、灵活、生态成熟 | 需自建分层/校验/文档，易写成"面条代码" | 小团队赶工期 |
| Fastify | 性能最好、Schema 校验原生 | 生态与装饰器支持弱于 Nest | 高并发网关场景 |

**推荐：NestJS**。理由：接口数量多（38 个）、需要清晰的模块边界（auth / conversation / knowledge / document / settings）、自带 `@nestjs/swagger` 能直接生成接口文档与前端契约对齐。

### 2.2 ORM 与数据库

| 方案 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **Prisma** | 类型安全、migration 优雅、TS 体验最好 | 复杂 SQL/向量查询需 `$queryRaw` | ✅ **推荐** |
| TypeORM | 装饰器实体、功能全 | 类型体验弱、维护活跃度下降 | 备选 |
| Sequelize | 老牌稳定 | TS 支持一般 | 不推荐 |

**数据库：PostgreSQL 16**（JSONB 支持配置存储、pgvector 扩展可省去独立向量库）。

### 2.3 向量库（关键决策）

| 方案 | 数据规模 | 运维成本 | 结论 |
| --- | --- | --- | --- |
| **pgvector** | ≤ 百万级切片 | 极低（与主库同实例） | ✅ **起步推荐** |
| Milvus | 千万级+ | 高（需独立集群、etcd、MinIO） | 规模上来后迁移 |
| Qdrant | 百万~千万 | 中 | 备选 |

**推荐：起步用 pgvector（`pg16 + pgvector 0.7+`，HNSW 索引）**。

理由：
- 一个 PostgreSQL 同时搞定业务数据 + 向量，Docker Compose 少 3 个容器
- 百万级切片在 HNSW 索引下召回延迟 <50ms，完全够用
- 检索层做一层抽象（`Retriever` 接口），后期换 Milvus 只改实现类

> 迁移触发条件：单知识库切片 > 200 万，或 P99 召回延迟 > 200ms。

### 2.4 任务队列

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| **Celery + Redis**（Python 侧） | 成熟、支持重试/定时/监控（Flower） | ✅ **推荐** |
| BullMQ（Node 侧） | Node 生态好，但 Python 消费不方便 | 不推荐跨语言 |
| FastAPI BackgroundTasks | 零依赖 | 仅 MVP 阶段临时用 |

**推荐：Celery(redis broker) + Flower 监控**。Python worker 消费任务、直接更新 PostgreSQL 中的文档状态，Node 不参与回调。

### 2.5 Python 技术栈

| 用途 | 选型（规划） | 实际落地 | 说明 |
| --- | --- | --- | --- |
| Web 框架 | **FastAPI** | ✅ 同规划 | 异步、SSE 用 `StreamingResponse` |
| 任务队列 | **Celery 5** | ✅ 同规划 | Redis broker（db 1），Flower 未部署 |
| PDF 解析 | **PyMuPDF (fitz)** | ✅ 同规划 | 字号启发式标题 + 线框表格转 MD + 页码保留 |
| Office 解析 | ~~MarkItDown~~ | ❌ 改用 **python-docx** | 仅需 docx，按 Heading 样式维护标题栈、表格按 body 顺序融合；xlsx/pptx/html 暂不支持 |
| 扫描件 OCR | ~~PaddleOCR~~ | ❌ 改用 **智谱 glm-ocr**（`/layout_parsing`） | 零本地依赖；`OCR_ENABLED` 开关 + `OCR_MAX_PAGES=20` 上限 |
| 切片 | **自研**（标题层级 + 递归字符） | ✅ 同规划 | 另加相邻小段合并（仅同标题）与 heading 路径注入 |
| Embedding | 本地 bge / 云端 API | ❌ 改用 **智谱 embedding-3**（1024 维） | 维度须与 `vector(1024)` 一致，换模型需全库重建 |
| Rerank | 本地 bge-reranker | ❌ 改用 **智谱 `/rerank`**（模型 ID 固定 `rerank`） | 失败自动回退 RRF 排名，不阻断 |
| 向量库客户端 | `pgvector-python` / `psycopg` | ✅ **psycopg3** + 裸 SQL | 词法召回直接用 pg_trgm 的 `%>` 操作符走 GIN 索引 |
| LLM SDK | `openai` SDK（兼容多家） | ✅ **httpx + OpenAI 兼容协议** | 智谱 BigModel 与 Moonshot 均兼容，无需额外 SDK |

### 2.6 模型选型（成本敏感，重点分析）

| 能力 | 本地部署方案 | 云端 API 方案 | 建议 |
| --- | --- | --- | --- |
| **LLM** | Qwen2.5-7B/32B + vLLM（需 GPU ≥16G） | 通义 qwen-plus / DeepSeek-V3（约 ¥1~4 / 百万 token） | **起步用云端**，有 GPU 再切本地 |
| **Embedding** | bge-large-zh-v1.5（CPU 可跑但慢，GPU 最佳） | text-embedding-v3（通义，约 ¥0.07 / 百万 token） | **起步用云端 bge-m3 或通义** |
| **Rerank** | bge-reranker-large（需 GPU 才能低延迟） | 部分厂商提供 Rerank API | **P3 阶段再上** |

> **MVP 最小成本方案**：全部走云端 API，**零 GPU 即可跑通全链路**。
> ✅ **实际落地**：智谱 BigModel 一站式（生成 GLM-4-Flash + 向量 embedding-3 + rerank + OCR glm-ocr），另接入 Moonshot Kimi K2.6 作为可选生成模型（会话级切换）。后续按数据敏感度与成本决定是否本地化。

### 2.7 对象存储

**MinIO**（S3 兼容，Docker 一键起）。自部署可控，避免云厂商绑定。生产可替换为 OSS/S3，只需换 SDK 配置。

## 三、系统架构

### 3.1 部署拓扑

```
                          ┌──────────────────┐
   浏览器 ──HTTPS─────────►│   Nginx (反向代理) │
                          └────────┬─────────┘
                    ┌──────────────┴──────────────┐
                    │                             │
          ┌─────────▼─────────┐        ┌──────────▼─────────┐
          │   Node BFF :3000   │        │  静态资源 (dist/)   │
          │   NestJS           │        └────────────────────┘
          └────┬────────┬─────┘
               │        │
      ┌────────▼──┐  ┌──▼──────────────────────────┐
      │ PostgreSQL │  │  Python AI Service :8000     │
      │ + pgvector │◄─┤  FastAPI + Celery Worker     │
      └────────────┘  └──┬──────────┬───────────┬───┘
                         │          │           │
                    ┌────▼───┐ ┌────▼────┐ ┌────▼──────┐
                    │ Redis  │ │ 文件存储 │ │ LLM/Emb API│
                    │ 队列   │ │(本地磁盘*│ │  (云端)    │
                    └────────┘ │ /MinIO) │ └───────────┘
                               └─────────┘
```

> \* **现状**：MVP 文件存本地磁盘 `server/uploads/<kbId>/`，MinIO 容器定义就绪（`docker-compose.infra.yml --profile storage` 可选启用），切换时仅需替换 `document.service.ts` 读写两处，契约不变。

### 3.2 两条核心链路

**链路 A：文档入库（异步）**（✅ 已跑通）

```
前端上传（白名单 pdf/docx/txt/md/csv，单文件 ≤20MB，一次 ≤10 个）
    → Node 落盘 server/uploads/<kbId>/ → 插 document(status=pending)
    → HTTP 调 Python /internal/tasks/parse（fire-and-forget，失败停留 pending）
    → 立即返回
Python: /internal/tasks/parse 入 Celery 队列 → Worker:
    路径校验（防穿越）→ 解析 → 切片 → Embedding → 写 chunks + 向量
    → 更新 document(status=parsed, chunk_count, progress=100)
    （ValueError 确定性错误 → 立即 failed；网络/限流类 → 指数退避重试）
前端: 轮询文档列表看进度
```

**链路 B：问答（流式）**（✅ 已跑通）

```
前端 POST /chat/completions → Node 鉴权/取会话上下文（先落库 user 消息再流式）
     → HTTP 调 Python /internal/chat (stream)
Python: 查询改写 → 混合检索(向量 + pg_trgm 词法) → RRF 融合 → rerank 精排
     → 组装 Prompt（context 预算截断 + 强制引用编号）
     → LLM 流式生成（glm-*→智谱 / kimi-*→Moonshot）→ SSE 返回 references/delta/done/error
Node: 逐块透传给前端 → done 后落库 assistant 消息 + message_sources；中途断开 abort 上游并落库 stopped
```

```ts
@Post('chat/completions')
async completions(@Body() dto: ChatDto, @Req() req, @Res() res: Response) {
  // sse.writer.ts：设置 text/event-stream 等响应头（含 X-Accel-Buffering: no），
  //               提供 references()/delta()/done()/error()/ping() 统一写出方法
  const writer = new SseWriter(res)

  // 先落库 user 消息（断线后历史不丢），再转发上游
  const userMsg = await this.chatService.appendUserMessage(dto)

  const upstream = await this.ai.streamChat({ ...dto, history })   // fetch + ReadableStream
  req.on('close', () => upstream.abort())     // 前端断开 → 中断上游 → 落库 stopped

  for await (const ev of upstream.events) {
    writer.forward(ev)                        // references/delta 透传，done 时落库
  }
  // done：assistant 消息 + message_sources（仅坐标）+ 会话冗余计数 + daily_stats 一起写入
  res.end()
}
```

**已落地的 5 件事**：
1. `X-Accel-Buffering: no`（Nginx 部署时还需 `proxy_buffering off`，见第九章）
2. 前端断开时 `abort()` 上游，assistant 消息落库为 `stopped`
3. 每 15 秒发一行 `:ping\n\n` 心跳，防代理超时断连
4. `done` 事件到达后落库消息（含 `message_sources` 坐标），落库失败不影响已发出的流
5. Python 不可达或 `AI_MOCK=true` 时走 Node 内置模拟流（保留用于离线演示），事件协议一致

#### (4) 文件上传（实际实现）

**切片**（`app/chunker.py`，实际实现）：

1. 按解析输出的标题块切分，保留页码；heading 非空时作为切片首行注入，使 embedding 携带章节上下文
2. 超过 `chunk_size` 的块，用递归分隔符切：`\n\n` → `\n` → `。` → `，` → 空格，块间按 `chunk_overlap` 重叠

### 6.3 检索链路（实际实现：`app/retrieval.py`）

```python
def search(kb_ids, query, top_k, threshold, hybrid, rerank):
    # 1. 向量召回：1 - cosine distance，取候选池（top-N，N 远大于 topK）
    vec_results = vector_recall(kb_ids, query, pool_size)

    if hybrid or rerank:
        # 2. 词法召回（独立一路）：pg_trgm word_similarity（%> 操作符走 GIN 索引，
        #    word_similarity_threshold=0.1 放宽短查询准入）
        lex_results = lexical_recall(kb_ids, query, pool_size)   # 失败自动降级池内 bigram Jaccard
        # 3. RRF 融合（k=60）：两路独立召回取并集后按倒数排名融合；
        #    向量分低于 threshold 的切片须词法分 ≥ 0.2 才保留
        candidates = rrf_fuse(vec_results, lex_results)
    else:
        candidates = vec_results

    # 4. Rerank 精排（智谱 /rerank，模型 ID 固定 rerank）：query-doc 交叉打分，
    #    失败时回退 RRF 排名不阻断；score 字段保持原语义（向量分优先）
    if rerank and candidates:
        candidates = rerank_results(query, candidates)

    # 5. 阈值过滤 + 截断
    return [c for c in candidates if c.score >= threshold][:top_k]
```

**与原方案的差异**：BM25（需分词器）改为 **pg_trgm word_similarity**——中文短查询对长文本无需分词即可工作，且 `GIN(chunks_content_trgm_idx)` 索引保证性能；多知识库为单条 SQL `kb_id = ANY(...)` 一次召回（非按库分别召回再合并）。

**相似度归一化**：pgvector 的 `<=>` 返回余弦距离，`score = 1 - distance`，与前端展示的百分比一致。

### 6.4 LLM 编排与提示词（实际实现）

```python
@celery_app.task(bind=True, max_retries=3)
def parse_document(self, doc_id: str):
    try:
        doc = fetch_document(doc_id)
        # 路径穿越防护：storage_key 解析后必须仍位于 upload_root 内
        root = os.path.abspath(settings.upload_root)
        path = os.path.abspath(os.path.join(root, *doc.storage_key.split('/')))
        if not path.startswith(root):
            raise ValueError(f'非法的文件路径: {doc.storage_key}')

        set_doc_status(doc_id, 'parsing', progress=0)
        blocks = parse_file(path, doc.type)                 # → [{page, text, heading}]
        chunks = chunk_blocks(blocks, doc.kb.chunk_size, doc.kb.chunk_overlap)
        if not chunks:
            raise ValueError('切片结果为空')
        set_doc_status(doc_id, 'indexing', progress=40)

        embeddings = embed_batch([c['content'] for c in chunks])   # 智谱 embedding-3 批量
        save_chunks_and_vectors(doc_id, chunks, embeddings)
        set_doc_status(doc_id, 'parsed', progress=100,
                       extra_sql='chunk_count = %s', params=(len(chunks),))
    except ValueError as exc:
        # 确定性错误（非法路径/无文本/空切片）：立即永久失败，重试无意义
        set_doc_status(doc_id, 'failed', progress=100, extra_sql='error_msg = %s', params=(str(exc),))
    except Exception as exc:
        # 网络/限流等瞬时错误：指数退避重试
        set_doc_status(doc_id, 'failed', progress=100, extra_sql='error_msg = %s', params=(str(exc),))
        raise self.retry(exc=exc, countdown=2 ** self.request.retries * 10) from exc
```

**重试策略要点**（v0.8.0 修复）：`ValueError` 视为确定性错误立即永久失败，不再进入指数退避空转；其余异常（网络抖动/限流）保留重试。修复后重试日志不再出现。

- 进度上报：解析 0 → 向量化 40 → 收尾 100
- 失败保留 `error_msg`，前端表格红字展示；`/reparse` 可人工补救

## 八、关键难点与解决方案

| # | 难点 | 影响 | 解决方案 |
| --- | --- | --- | --- |
| 1 | **SSE 被中间层缓冲** | 流式退化成一次性返回 | 响应头 `X-Accel-Buffering: no`；Nginx 配置 `proxy_buffering off; proxy_read_timeout 300s;` |
| 2 | **前端断开后上游继续推理** | 浪费 GPU/token | `req.on('close')` → `AbortController.abort()`；Python 侧检测连接断开中断生成 |
| 3 | **大文件解析阻塞请求** | 接口超时 | 全异步：上传立即返回，Celery 消费，前端轮询进度 |
| 4 | **Embedding 速度慢** | 入库耗时长 | 批量调用（32/批）；云端 API 并发；本地则上 GPU |
| 5 | **向量库迁移成本** | 后期换 Milvus 返工 | 抽象 `VectorStore` 接口，业务层不感知具体实现 |
| 6 | **引用来源与文档改名不同步** | 引用显示旧文件名 | `message_sources` 只存坐标，展示时 JOIN |
| 7 | **模型幻觉** | 回答不可信 | 三道防线（见 6.4） |
| 8 | **知识库删除的级联清理** | 残留脏数据 | 事务内删业务数据 → 异步任务清理 MinIO + 向量 |
| 9 | **多知识库检索的权重** | 结果倾斜 | 先按 kb 分别召回再归一化合并，避免大库霸榜 |
| 10 | **pgvector 性能拐点** | 召回变慢 | 监控 P99；达阈值后迁移 Milvus（接口层已抽象） |

## 九、部署方案

### 9.1 服务清单（✅ Docker 全栈编排已交付）

**交付物（2026-09-08）**：`docker-compose.yml`（统一单文件，project name `kb-prod` 与开发环境隔离）+ 三个 Dockerfile（`frontend/`、`server/`、`ai-service/`，均多阶段构建）+ `nginx/default.conf`（托管 dist + /api 反代 + SSE 关缓冲）+ `.env.docker.example`（密钥模板）+ 各 `.dockerignore`。

**一键部署**：

```bash

docker compose up -d --build  # server 容器首启自动 prisma migrate deploy + seed admin
```

**关键设计**：

| 项 | 方案 |
| --- | --- |
| 共享上传卷 | `uploads_data` 同时挂 server 与 worker 的 `/app/uploads`（Node `cwd/uploads` 落盘、Python `UPLOAD_ROOT=/app/uploads` 读取） |
| 数据库迁移 | server entrypoint 首启 `prisma migrate deploy` + 幂等 seed（seed.ts 构建期预编译为 JS） |
| 网络隔离 | 仅 nginx 映射宿主端口（`NGINX_PORT`，默认 80）；postgres/redis/ai-service 仅容器网络内可达 |
| SSE | nginx `proxy_buffering off` + `proxy_read_timeout 300s` + `Connection ''` |
| 上传体积 | nginx `client_max_body_size 256m`（对应 10×20MB 多文件 + 12MB base64 附件） |
| CORS | 同源反代后浏览器请求同源，`FRONTEND_URL` 仅作显式白名单 |
| 镜像基座 | Node 用 slim（规避 Prisma/alpine openssl 问题）、Python 3.12-slim（依赖全有 wheel，无编译依赖） |

**现状（本机开发/演示）**：`docker-compose.infra.yml` 只起基础设施——`kb-postgres`（pg16+pgvector, :5432）、`kb-redis`(:6379)、`minio`（`--profile storage` 可选）；Node BFF（:3000）与 Python API（:8000）+ Celery worker 以进程方式本机启动，与生产编排互不影响。
