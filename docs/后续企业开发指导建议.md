# 后续企业开发指导建议

> 本文回答一个问题：**如果这套系统要真实交付给企业使用，需要做哪些改造**。
> 现状是功能完整的教学/演示系统；企业化改造分三条主线：权限下沉、存储演进、模型私有化。

---

## 一、文档级权限体系（优先级最高）

### 1.1 现状与差距

| | 现状 | 企业要求 |
| --- | --- | --- |
| 权限粒度 | 知识库级（internal / public / private，见 `server/src/common/kb-access.ts`） | 文档级，甚至片段级 |
| 角色模型 | admin / member 两角色 | 部门 + 密级 + 人员授权 |
| 过滤位置 | 应用层（进库后可查全库） | **检索层**（SQL 谓词内过滤） |
| 审计 | operation_logs 记录操作 | 增加"查阅机密文档"审计 |

进库即可查全库——企业里"能进项目库"≠"能看薪酬表"，所以权限必须下沉到文档。

### 1.2 数据模型草案

```prisma
model Document {
  // ...现有字段
  sensitivity  String    @default("internal")  // public | internal | secret | confidential
  ownerDeptId  String?                         // 归属部门
  aclEntries   DocumentAcl[]                   // 附加授权（人员/部门白名单）
}

model DocumentAcl {
  id         String   @id @default(cuid())
  documentId String
  subjectType String  // user | dept | role
  subjectId  String
  @@unique([documentId, subjectType, subjectId])
}
```

密级建议采用四级：`公开 → 内部 → 秘密 → 机密`，与角色上的"最高可读密级"字段做比较。

### 1.3 核心原则：权限过滤必须在检索层

**错误做法**（应用层后过滤）：先召回 top-k，再在 Node 层剔除无权限片段。
问题：① 浪费召回名额（top-k 可能全被剔光）；② 片段已离开数据库，可能在日志/异常/流式事件中泄露。

**正确做法**（检索层谓词过滤）：把"当前用户可读的文档集合"作为 SQL 条件直接参与向量检索：

```sql
SELECT id, content, 1 - (embedding <=> $query_vec) AS score
FROM chunks
WHERE kb_id = $1
  AND document_id IN (          -- 权限谓词与向量检索同一查询
    SELECT id FROM documents
    WHERE sensitivity <= $user_max_level
       OR id IN (SELECT document_id FROM document_acls WHERE subject_id = $user_id)
  )
ORDER BY embedding <=> $query_vec
LIMIT $k;
```

词法路（pg_trgm）与 rerank 候选池同理。**这是当初选 pgvector 单库的意外红利**：权限 JOIN 和向量排序在同一个 SQL 里完成；若向量库独立（Milvus/FAISS），跨库权限过滤要先把授权文档 id 列表拉到内存再传给向量库，规模一大就很脆弱——选型回顾时这是"当时无意识、事后被验证"的真实论据。

### 1.4 配套要求

- **审计日志**：记录"谁、何时、以什么密级查看了什么文档"，机密级文档的每次命中单独成表，保留期按企业合规要求（通常 ≥ 6 个月）
- **密级物理隔离**：最高密级知识库独立部署实例（独立 compose 项目 + 独立数据库），网络层不与普通实例互通
- **前端配合**：检索结果中对无权限片段不显示占位条目（避免通过"这里有条被隐藏的结果"探测密级）

## 二、部署形态与存储演进

### 2.1 三种部署形态（按数据敏感度选）

| 形态 | 数据位置 | 适用 | 本项目落地方式 |
| --- | --- | --- | --- |
| **私有化（on-premise）** | 企业自己机房 | 机密文件的主流选择，数据不出内网 | docker-compose.prod.yml 原样部署到企业服务器 |
| 私有云（企业 VPC） | 企业租用的云，逻辑隔离 | 中等敏感 | 同上，机器换成云主机 |
| 公有云 SaaS | 厂商多租户环境 | 仅公开/内部资料 | 需先补多租户隔离（超出本文范围） |

关键认知：**"上云"不是企业化的必要条件**。文件现在就存在服务器本地卷（`uploads/`），向量在 Postgres——部署到企业内网即数据不出企业。

### 2.2 对象存储升级路径

本地卷在单机演示没问题，企业版替换为对象存储：

1. **MinIO（推荐首选）**：私有化 S3 协议对象存储，一个容器即可跑在企业内网，与现有uploads 共享卷语义最接近；改造成点集中在 `server` 的上传/下载两个模块
2. 云厂商 OSS / COS：仅当企业选择公有云形态
3. 保留本地卷作为开发模式默认值，通过环境变量切换存储后端（策略模式封装 `StorageService`）

### 2.3 数据可靠性底线

- Postgres：每日 `pg_dump` 定时任务 + 命名卷快照（参考启动指南"备份与恢复"节）
- 对象存储：MinIO 开版本控制或镜像到备份盘
- Redis 可不备份（队列丢了最多重传解析任务）

## 三、模型私有化（最容易被忽略的硬要求）

### 3.1 问题：LLM API 本身就是数据出口

文件存在自己机房 ≠ 数据不出企业。当前架构下：

- 每次问答：**检索到的文档片段原文**会随上下文发给智谱/Moonshot 的生成 API
- 每次解析：**全部文档切片**会发给 embedding API 做向量化
- 扫描件：页面图像会发给 OCR API

企业安全官的第一个问题就会是这个。机密级知识库接第三方 API 等于数据出境。

### 3.2 解决方案：切换本地开源模型

| 用途 | 现用 | 私有化替代 |
| --- | --- | --- |
| 生成 | GLM / Kimi API | Qwen2.5-14B/32B-Instruct（vLLM 部署，单卡 24G 起） |
| 向量化 | embedding-3 API | bge-m3（CPU 即可，GPU 更快） |
| 精排 | rerank API | bge-reranker-v2-m3 |
| OCR | glm-ocr API | PaddleOCR（本地库） |

**架构上的有利条件**：`ai-service/app/llm.py` 与 `embedding.py` 均为注册表设计，模型路由按名称前缀分发——私有化 Provider 只需注册新的前缀（如 `local-*` → `http://vllm:8000/v1`），调用方代码零改动。OpenAI 兼容协议（vLLM/Xinference/Ollama 均提供）意味着生成与向量的接入成本很低。

### 3.3 分级接入策略（不必一步到位）

- 内部/公开知识库：可继续用云端 API（成本低、效果好），签企业协议 + 关闭训练用途条款
- 秘密/机密知识库：强制走本地模型路由（可按知识库配置 `modelPolicy` 字段实现路由隔离）

## 四、实施路线图

| 阶段 | 改造项 | 主要涉及 | 复杂度 |
| --- | --- | --- | --- |
| **P0** | 文档密级字段 + 检索层权限谓词 | schema.prisma / retrieval.py / kb-access.ts | 中 |
| **P0** | 机密文档查阅审计 | operation_logs 扩展 + 查询侧埋点 | 低 |
| **P1** | 存储后端抽象（本地卷 / MinIO） | server 上传下载模块 | 中 |
| **P1** | 本地 embedding + reranker 接入 | embedding.py 注册表 + GPU/容器编排 | 中 |
| **P1** | 按知识库的模型路由策略（modelPolicy） | config.py / llm.py / conversations 表 | 低 |
| **P2** | 本地 LLM（vLLM + Qwen） | 新增 vllm 容器 + llm.py 注册 | 高 |
| **P2** | 密级物理隔离（双实例部署） | compose 拆分 + 网络策略 | 中 |
| **P2** | 多租户 SaaS 化（如选公有云形态） | 全链路租户隔离改造 | 高 |

## 五、企业交付安全清单

- [ ] 全部密钥（JWT/DB/内部令牌/API Key）使用企业密钥管理系统或至少独立的密钥托管，禁止明文进 git
- [ ] 默认账号 admin 首登强制改密；注册开关默认关闭
- [ ] HTTPS（nginx 挂证书），内部令牌仅限容器内网
- [ ] 上传白名单、大小限制复核；病毒扫描按企业要求接入（ClamAV）
- [ ] 日志与审计的保留周期、导出能力符合企业合规（等保/行业规定）
- [ ] 演示数据与生产数据严格分离；交付前清空 seed 数据
- [ ] 明确数据边界文档：哪些环节有数据出企业（接 API 的模块清单），签 DPA
