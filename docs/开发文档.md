## 一、项目概述

面向企业的 RAG（检索增强生成）知识库问答系统。用户上传企业文档，系统完成解析、切片、向量化后，即可通过自然语言提问并获得**可溯源**的回答。

### 1.1 技术选型

| 层级 | 技术 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3 + Vite 6 + Element Plus | 组合式 API（`<script setup>`）、Pinia 状态管理、Vue Router |
| BFF 层 | **NestJS 12 + TypeScript 5.9 + Prisma 6**（已落地） | 鉴权、业务编排、会话与知识库元数据、SSE 转发 |
| AI 服务 | Python FastAPI + Celery（已落地） | 文档解析、切片、Embedding、混合检索、Rerank、LLM 推理（多 Provider） |
| 存储 | PostgreSQL 16 + pgvector（已落地）+ Redis（已落地）+ MinIO（暂用本地磁盘，容器可选启用） | 业务数据 / 向量（HNSW 索引）/ 任务队列 / 文件存储 |
| 模型 | 智谱 BigModel + Moonshot Kimi（均已落地） | GLM 生成、embedding-3 向量、rerank 精排、glm-ocr；Kimi K2.6 可选生成模型 |

cd frontend

# 2. 安装依赖（Node >= 18，推荐 20+）

### 2.4 一键启动（推荐）

项目共 4 组服务，`scripts/` 下提供一键脚本（**按端口精确启停，不影响机器上其他进程**；脚本幂等，已在运行的服务自动跳过）：

```powershell
# 启动（基础设施 → AI 服务 → 后端 → 前端）
powershell -ExecutionPolicy Bypass -File scripts\start-all.ps1

# 停止（按端口杀 5173/3000/8000 + 按命令行特征杀 celery）
powershell -ExecutionPolicy Bypass -File scripts\stop-all.ps1
```

| 顺序 | 服务 | 端口 | 说明 |
| --- | --- | --- | --- |
| 1 | Docker：kb-postgres / kb-redis | 5432 / 6379 | 未运行则 `docker start` |
| 2 | Python AI：uvicorn + celery worker | 8000 | 日志 `ai-service/api.log`、`celery.log` |
| 3 | Node BFF | 3000 | 日志 `server/run.log`；**改了 ts 代码需先 `npm run build`** |
| 4 | 前端 Vite | 5173 | 开发模式热更新 |

访问入口：前端 http://localhost:5173（admin/admin123）· 后端 http://localhost:3000/api/v1 · AI 健康检查 http://127.0.0.1:8000/internal/health

> 注意：① 脚本为 ASCII 文案——Windows PowerShell 5.1 对无 BOM 的中文 ps1 会按 GBK 解析报语法错误；② `stop-all` 不会停 Docker 容器；③ 前端代码改动 Vite 自动热更新，无需重启。

## 四、前端架构

### 4.1 分层职责

```
视图层 views/  ──►  状态层 store/  ──►  接口层 api/  ──►  后端 / Mock
                        ▲
                        └── 组件 components/ 只做展示与事件抛出
```

- **views**：负责页面布局与业务流程编排，不直接写请求逻辑
- **components**：纯展示组件，通过 props 接收数据、emit 抛出事件
- **store**：持有业务状态，调用 `api/` 完成数据读写
- **api**：唯一的数据出入口，内部按 `USE_MOCK` 决定走 Mock 还是真实 HTTP

### 4.2 路由设计

| 路径 | 页面 | 说明 |
| --- | --- | --- |
| `/login` | 登录 | `meta.public = true` |
| `/chat` | 问答首页 | 新对话状态，发送首条消息后跳转 `/chat/:id` |
| `/chat/:id` | 指定会话 | 加载历史消息 |
| `/knowledge` | 知识库列表 | 卡片视图 + 新建 |
| `/knowledge/:id` | 知识库详情 | 文档管理 / 检索测试 / 配置 / 统计四个 Tab |
| `/settings` | 系统设置 | 模型 / 检索 / 安全 / 密钥 / 用户 / 日志 |
| `/:pathMatch(.*)*` | 404 | — |

登录守卫位于 `router/index.js`：未登录访问非 public 路由跳转登录页，已登录访问登录页跳转 `/chat`。

### 4.3 状态管理

**chat store（核心）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `conversations` | Array | 会话列表 |
| `currentId` / `current` | String / Object | 当前会话 ID 与详情 |
| `messages` | Array | 当前会话消息流 |
| `streaming` | Boolean | 是否正在生成 |
| `stage` / `stageText` | String | `searching` / `generating` 阶段提示 |
| `controller` | Object | 流控制器，用于中断生成 |

关键方法：`sendQuestion` / `regenerate` / `stopStream` / `feedback` / `openConversation` / `renameConversation` / `togglePin`。

**知识库 store**：`list` / `current` / `documents` / `options`，方法覆盖增删改查、上传、重建索引、重新解析。

**用户 store**：`token` / `profile` / `isLogin` / `isAdmin` / `permissions`。

### 4.4 Mock 机制

- 所有 Mock 数据集中在 `src/mock/`，运行时维护在内存数据库 `mockDb`，刷新页面即还原初始状态
- `api/*.js` 中每个函数均采用「Mock / 真实」双分支：

```js
export function getKnowledgeList(params) {
  if (USE_MOCK) {
    /* 本地模拟，返回与后端一致的数据结构 */
    return mockOk(paginate(list, page, pageSize))
  }
  return request({ url: '/v1/knowledge', method: 'get', params })
}
```

- 后端就绪后：① 将 `.env.development` 的 `VITE_USE_MOCK` 改为 `false`；② 删除 `src/mock/` 目录即可，业务代码零改动
- 检索模拟采用字符二元组相似度（`mock/index.js#similarity`），配合关键词与随机抖动，效果接近真实向量召回的排序表现
- 流式输出由 `request.js#mockStreamText` 按 2~6 字符切片、16~40ms 间隔推送，并返回 `abort()` 控制器

### 4.5 问答数据流（时序）

```
用户输入
  │
  ├─► store.sendQuestion()
  │     1. 无会话则先 createConversation
  │     2. 乐观插入 user 消息 + assistant 占位消息
  │
  ├─► api.streamAnswer()
  │     ├ onStage('searching')  → 消息区展示「正在检索知识库…」
  │     ├ onStage('generating') → 携带 sources，展示「已找到 N 个相关片段」
  │     ├ onChunk(piece)        → 追加到占位消息 content（Markdown 实时渲染）
  │     └ onDone({sources,meta})→ 写入状态 / 用量 / 耗时
  │
  ├─► 首条提问自动以问题前 20 字作为会话标题
  ├─► persistMessages() 回写 Mock 库（真实后端由服务端持久化，无需此步）
  └─► fetchConversations() 刷新侧边栏列表
```

## 六、后端规划（Node + Python）

> 本章为下一阶段的实施建议，前端接口层已按此契约预留。

### 6.1 服务分层

```
浏览器 ──HTTPS──► Node BFF（3000）
                    ├── 鉴权 / 会话 / 知识库元数据（PostgreSQL）
                    ├── 文档任务编排（Redis 队列）
                    ├── 文件对象存储（MinIO）
                    └── SSE 转发 ──► Python AI 服务（8000）
                                        ├── 文档解析（PDF/Word/Excel/PPT/MD/OCR）
                                        ├── 切片 + Embedding
                                        ├── 向量检索（Milvus/pgvector）+ BM25 + Rerank
                                        └── LLM 推理编排（流式返回）
```

**职责划分**

| 能力 | 归属 | 说明 |
| --- | --- | --- |
| 用户鉴权、会话、知识库元数据 | Node | 事务型业务，CRUD 为主 |
| 文件上传与任务编排 | Node | 生成解析任务，写入 Redis 队列 |
| 文档解析、切片、向量化 | Python | CPU/GPU 密集，异步消费队列 |
| 向量检索、Rerank | Python | 检索链路与参数实验 |
| LLM 推理与 SSE 流 | Python | 由 Node 转发 SSE 给前端 |

### 6.3 关键实现要点

1. **SSE 流式协议**：事件类型固定为 `references` / `delta` / `done` / `error`，详见[接口文档](./接口文档.md#五问答流式接口sse)
2. **引用来源落库**：消息只存引用坐标（`kbId` / `docId` / `chunkIndex` / `score`），展示时再关联文档信息，避免文档改名后引用失效
3. **文档解析异步化**：上传立即返回，前端通过轮询或 SSE 接收进度（`doc.status`：`pending → parsing → indexed → failed`）
4. **抑制幻觉**：检索低于阈值直接返回兜底话术；生成阶段强制引用编号；展示层提供原文核对
5. **限流与配额**：按 API Key 与用户双维度限流，返回 `429` + `Retry-After`

#### 6.4.2 SSE 时序（`POST /chat/completions`）

```
前端 POST /chat/completions (JWT)
 1. 鉴权 + 校验会话归属；conversationId 为空 → 服务端代建（标题=问题前20字）★已确认
 2. 落库 user 消息 → 落库 assistant 占位消息(status=streaming)   ← 先持久化再流式
 3. 取最近 5 轮历史组装上下文
 4. 调 Python POST /internal/chat (SSE)，逐事件：
      references → 批量 JOIN documents/knowledge_bases 补全 docName/kbName/snippet
                 → 落库 message_sources（只存坐标，按 sortOrder）
                 → 透传
      delta      → 累积正文 + 原样透传
      done       → 回写 assistant(content/meta/status=done) → 累加 tokenUsed/messageCount → 透传
      error      → 消息置 status=error → 透传
 5. 前端断开(req close) → AbortController.abort() 上游
      → 已收正文落库，消息置 status=stopped
 6. 心跳：每 15s 写 `: ping\n\n`（注释行，前端解析器天然忽略）
```

#### 6.4.3 与前端解析器对齐约定

- 只发 `data: {...}\n\n`，JSON 携带 `type`（不使用 `event:` 行）
- `references` → Source 数组；`delta` → `{content}`；`done` → `{messageId, conversationId, meta}`；`error` → `{message}`
- 响应头：`text/event-stream`、`no-cache, no-transform`、`keep-alive`、`X-Accel-Buffering: no`

### 6.5 Python AI 服务设计（v0.4.0 已实施方案）

> 2026-09-05 设计并经确认实施。**Embedding 与 LLM 统一走智谱 BigModel API**（OpenAI 兼容协议，`base_url=https://open.bigmodel.cn/api/paas/v4`）。

#### 6.5.1 职责与边界

```
Node(已完成)                     Python(本服务 :8000，仅内网)
上传落盘 → 投递解析任务 → 解析(PyMuPDF/python-docx/纯文本) → 切片 → Embedding → 写 chunks+向量
提问 → /internal/chat(SSE) ← 检索(pgvector) → Prompt组装 → GLM 流式
检索测试 → /internal/search
```

- **向量列独写权**：`chunks.embedding` 仅 Python 读写
- 文档状态机由 Python 更新：`pending → parsing → indexing → parsed / failed`
- Node 删除文档/知识库时，chunks 由 **FK 级联**自动清理，无需独立删除接口

#### 6.5.2 技术栈

| 项 | 选型 |
| --- | --- |
| Web | FastAPI + uvicorn（:8000，绑 127.0.0.1） |
| 队列 | Celery 5 + Redis(db1)，Windows 下 `--pool=solo` |
| 数据库 | psycopg3（连接池）+ 原生 SQL，向量以 `'[..]'::vector` 字面量写入 |
| 解析 | PyMuPDF（PDF 按页，字号启发式标题识别、线框表格转 Markdown）、python-docx（docx 按 Heading 样式）、直接读取（md/txt/csv，utf-8/gb18030 编码探测）；**扫描件 PDF 走智谱 glm-ocr 兜底**（`/layout_parsing`，单文档 ≤20 页）；xlsx/pptx/html 留 P3 |
| Embedding | 智谱 `embedding-3`，**必须显式 `dimensions=1024`**（默认 2048 与 vector(1024) 不匹配）；另留 `mock` 档跑管道 |
| 检索 | 向量 + pg_trgm `word_similarity` 词法双路独立召回 → RRF 融合（k=60）→ 智谱 rerank 精排（失败回退 RRF 排序，不阻断），见 6.8 |
| LLM | **多 Provider**（见 6.11）：智谱 GLM（默认 `glm-4-flash`）+ Moonshot Kimi（`kimi-k2.6`），`openai` SDK 流式 |
| 运行 | 本机 venv 两进程（uvicorn + celery worker），Docker 化留生产 |

#### 6.5.4 解析任务状态机（Celery `parse_document(doc_id)`）

```
pending → parsing(10) → 读文件(UPLOAD_ROOT/<storageKey>，路径穿越防护) → 解析(文本+页码映射)
        → 切片(知识库 chunk_size/overlap，heading 注入首行+递归字符) → indexing(40)
        → 批量 Embedding(退避重试) → INSERT chunks(ck_ 前缀 ID，executemany) → parsed(100)
        → doc.chunk_count + kb.chunk_count 回算 + kb.status='ready'
```

**失败与重试策略**（v0.8.0 优化）：

| 错误类型 | 处理 |
| --- | --- |
| `ValueError`（确定性错误：非法路径、不支持的格式、空切片等） | 立即置 `failed + error_msg`，**永久失败不重试** |
| 其他异常（网络、限流等瞬时错误） | 置 `failed + error_msg` 后指数退避重试（`60 × 2^retries` 秒，Celery 最多 3 次） |

#### 6.5.5 检索与生成要点

- 检索：pgvector `<=>` 余弦距离，`score = 1 - distance`（与前端百分比口径一致），阈值过滤后返回；混合检索与 Rerank 已实现，见 6.8
- Prompt：`[1] 来源：xxx.pdf 第6页` 编号格式 + 强制引用标注（`forceCitation`：回答无 `[n]` 编号时自动追加「参考来源」列表）；`systemPrompt/fallbackReply` 由 Node 请求体传入（Python 无状态，不读 settings 表）
- context 字符预算：6000 字符（约 3000 token），按相关性排名截断（剩余 >200 字符时截断本段收尾）
- 相邻片段合并：同文档 `chunkIndex` 连续的检索结果合并，消除 overlap 重复、压缩引用条数
- 多轮查询改写：有历史时先以 LLM 消解指代/补全省略（改写失败回退原问题不阻断），改写后的查询记录在 `done.meta.rewrittenQuery`
- 兜底：最高分 < threshold（融合模式为「向量分与词法分均不达标」）→ `references([])` + fallback 话术，**不调 LLM**；有附件时附件文本可作答，不触发兜底
- token 用量：GLM/Kimi 响应 `usage` 真实回传；缺失时按字符数估算

#### 6.6.2 规则与安全

| 项 | 规则 |
| --- | --- |

## 六点八、检索参数调优（v0.6.0 已实施方案）

> 2026-09-06 设计并经确认实施。**目标**：让 KB 配置 / 会话级传入的 `topK / threshold / hybrid / rerank` 真正驱动检索；新增**混合检索（向量 + 词法）**与 **RRF 融合重排**，显著提升长尾 / 专有名词召回。
> 后续若接入专用重排模型（bge-reranker 等），仅在 Python 侧扩展 `rerank` 分支，接口契约不变，前端零改动。

### 6.8.1 设计要点

检索统一入口：`ai-service/app/retrieval.py#search(kb_ids, query, top_k, threshold, hybrid, rerank)`

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| 向量召回 | pgvector `<=>` 余弦，`score = 1 - distance`，阈值过滤 | 语义主召回，阈值语义保持不变 |
| 词法召回（中文友好） | Python 端**字符二元组（bigram）Jaccard** 打分 | Postgres 默认 FTS 不支持中文分词，故词法召回不依赖 DB 扩展；候选池取向量 top-N（`N=max(topK*4, 30)`）的切片内容计算 |
| RRF 融合重排 | 当 `hybrid \|\| rerank` 为真，对向量排名与词法排名做 Reciprocal Rank Fusion：`score = 1/(k+rv) + 1/(k+rl)`（k=60），按融合分重排输出 topK | 同时提升语义与关键词命中 |
| 防幻觉兜底 | 融合模式下切片需满足「向量分 ≥ threshold **或** 词法分 ≥ LEX_MIN(0.2)」方可入选；全池不满足则返回空 → 走 fallback 不调 LLM | threshold 语义在融合模式下依然有效，强关键词命中可越过阈值 |

### 6.8.2 参数贯通（端到端）

| 层 | 关键改动 |
| --- | --- |
| KB 配置 | `retrieverConfig {topK, threshold, rerank, hybrid, rerankModel}`；`resolveRetriever()` 现读 `hybrid` 并下传 |
| 会话级覆盖 | `ChatCompletionDto.retriever?: {topK?, threshold?, hybrid?, rerank?}`；chat.service 优先用其覆盖 KB 默认 |
| Node→Python | `InternalChatPayload` 增加 `hybrid?`；`/internal/chat`、`/internal/search` 均透传 |
| Python | `ChatRequest` / `SearchRequest` 增加 `hybrid`；`retrieval.search` 实现融合 |

默认：`DEFAULT_RETRIEVER.hybrid = true`（融合重排默认开启，召回更全），`rerank=true` 等价开启融合。

### 6.8.3 验收场景

| # | 场景 | 预期 |
| --- | --- | --- |
| 1 | `/internal/search` 关闭 hybrid | 纯向量，结果与旧版一致 |
| 2 | 开启 hybrid | 含关键词命中的切片排名上移，召回更全面 |
| 3 | 会话级传 `retriever:{threshold:0.1, hybrid:true}` | 本次问答命中更多片段 |

### 6.12 附件临时问答（已实施方案）

> 用户提问时可附带文件，文本提取后仅作为**本次回答**的上下文，不写入知识库、不产生向量。

#### 6.12.1 链路

```
前端 FileReader→base64
  → POST /chat/attachments {files:[{name, base64Content}]}（JWT）
  → Node 校验（白名单 pdf/docx/txt/md/csv、≤5MB、≤2 个）
  → POST /internal/extract（Python：base64 解码→临时文件→parser 提取→用后即删，文本截取 6000 字）
  → Node 暂存内存（attachmentIds ↔ 文本，按用户隔离）
  → POST /chat/completions 携带 attachmentIds
  → 内部请求 attachments:[{name, text}] 前置进 context
```

#### 6.12.2 引用规则（防悬空引用）

| 场景 | 处理 |
| --- | --- |
| 有知识库来源 + 附件 | 附件不占编号；提示词明确「`[n]` 仅对应知识库来源列表，附件内容直接提及文件名」 |
| 无知识库来源 + 附件 | 不使用 `[n]` 编号格式；要求模型自然提及所依据的附件文件名 |
| 检索为空 + 有附件 | **不触发兜底**，基于附件回答 |

#### 6.12.3 约束

- 单文件 ≤5MB（Python 侧同样校验 413）、每次 ≤2 个、文本截取 6000 字（`truncated=true` 标记）
- 附件文本不落库、不参与 Embedding，回答结束即失效

## 九、常见问题

**Q1：如何切换到真实后端？**
修改 `.env.development` 中 `VITE_USE_MOCK=false`，并在 `vite.config.js` 中确认代理地址正确。

**Q2：Mock 数据修改后不生效？**
`mockDb` 在应用启动时从静态数据克隆，修改 `src/mock/*.js` 后需重启 dev 服务（Vite 热更新对非组件模块不生效时手动刷新页面）。

**Q3：为什么回答没有引用来源？**
Mock 环境下未命中关键词语料时走兜底话术，此时无引用。可在知识库「检索测试」中下调阈值观察召回情况。

**Q4：会话切换后消息丢失？**
Mock 环境依赖 `persistMessages()` 回写内存库；若接入真实后端，消息由服务端持久化，无需该逻辑。

**Q5：如何新增一个知识库字段？**
依次修改：`src/mock/knowledge.js`（Mock 数据）→ `docs/接口文档.md`（契约）→ 对应页面表单与展示。

**Q6：控制台日志打了三遍 stage，但页面气泡一直停在「正在检索知识库…」，为什么？**
这是 Vue 3 响应式的「闭包陷阱」。`this.messages.push(rawObj)` 之后，Vue 会用 Proxy 包装这个对象，但本地变量仍持有原始对象引用。在原始对象上改属性会绕过 Proxy、不触发 UI 更新。
**正确写法**：

```js
this.messages.push(msg)
// ✗ 会绕过响应式：const target = msg
// ✓ 拿到 Proxy：
const idx = this.messages.length - 1
const apply = (fn) => { const t = this.messages[idx]; if (t) fn(t) }
apply((t) => { t.content += piece })
```

判断技巧：回调里能 `console.log` 看到数据变化但 UI 没动，**100% 是这个问题**。

**Q7：HMR 后 store 改动没生效？**
Vite 对 store 文件的热更新不可靠。**遇到 store 类改动一律 Ctrl + Shift + R 强制刷新**，避免调试时误导。
