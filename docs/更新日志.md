## v0.9.66 — 2026-10-26

### 修复：用户问「发原图给我」模型仍道歉说无法发图

> 用户实测：问「境界是怎么划分的」命中 PDF 文本切片正常；追问「请把原图发送给我」时模型回答「抱歉，我无法直接发送原图」。方案 B 能力本身正常（命中图片切片时引用区自动渲染原图），坏在两层：

- **模型不知道插图机制**：LLM 收到的图片切片只是「【文档插图 · 图说】…」文本，它不知道「该引用的原图已自动展示给用户」，于是诚实（但错误）地道歉。修复（[internal.py](/ai-service/app/api/internal.py)）：命中图片切片时 system prompt 追加 IMAGE_AWARE_PROMPT（说明插图已展示在引用区，要求引导用户查看而非道歉）；build_context 对图片切片头部标注「文档插图，原图已自动展示在引用来源中」
- **图片切片进不了 Top-K**：图说是图中文字的描述，与「把原图发给我」这类指令问句语义距离远，正常排序根本召不回插图。修复（[retrieval.py](/ai-service/app/retrieval.py)）：图片意图兜底——问题含「图/图片/原图/插图/图表…」意图词且结果无插图时，从命中库补一张向量最相似的图片切片（忽略阈值，LIMIT 1，chunkId 去重，失败不影响主检索）；意图探测传用户原话（`intent_text`）——多轮改写消解指代后会丢「图」字
- **deploy 首轮实测踩坑**：兜底补进的图片切片被 `merge_adjacent` 相邻合并吞掉（图片切片 chunkIndex 紧跟文本切片，合并后组头是文本 → imageId 丢失，引用区永远 null）→ 修复：merge_adjacent 不再跨类型合并（imageId 非空的切片恒独立）；换措辞复测通过
- **部署**：ai-service 单镜像 v0.9.66；实测「文档里那张天梯图的原图可以给我看看吗」→ 引用含 imageId=img_a1ba653bedd8 + 模型回答「可以，原图已自动展示在下方的引用来源区域中」+ 引用区渲染原图

## v0.9.65 — 2026-10-26

### 修复：登录过期风暴与「重新登录后仍提示已过期」

> 用户报告：令牌过期后自动失去登录状态；重新登录后仍弹「登录已过期，请重新登录」。排查确认无感刷新（v0.9.55/56）本身已实现且单飞，真正的坑在两处竞态。

- **Bug 1 · forceRelogin 竞态风暴（主凶，前端）**：token 过期瞬间页面并发 N 个请求全部 401 → 刷新失败时 N 个 catch 同时调 forceRelogin → 弹 N 次提示 + N 个 600ms 跳转定时器。用户 20 秒后重新登录成功，迟到的定时器仍触发 `location.href='/login'` 把刚登录的用户拽回登录页——表象正是「重新登录后仍显示登录已过期」。修复（[request.js](/frontend/src/api/request.js)）：forceRelogin 幂等化（一轮登出只处理一次）+ 延迟 600ms 后二次确认（期间 localStorage.kb_token 被重新写入 → 放弃提示与跳转）；新增 `notifyAuthRecovered()`，login/register 成功后复位登出流程（[user.js](/frontend/src/api/user.js)）
- **Bug 2 · 多标签页 refresh 轮换互踢（次凶，后端）**：多标签共享 localStorage，access token（2h）同刻过期时各标签独立刷新；严格 GETDEL 下后到的一方 401 → 被强制登出**且顺手清掉别页刚换的新令牌**（两个标签全下线）。修复（[auth.service.ts](/server/src/auth/auth.service.ts)）：轮换后旧 refresh token 保留 **60s 宽限 key**（`login:rt:grace:{jti}`），窗口内后到的刷新同样换到新令牌对；重放风险收敛到 60s；登出/改密（tokenVersion 自增）时宽限 key 一并吊销，全端下线语义不变
- **e2e 适配**：「并发双花一成一败」改为「宽限下并发均可成功（多标签互不踢）」；「重放 401」改为「宽限窗口内可换、窗口外由 TTL 天然拒绝」；登出吊销/改密失效用例不变（仍 401）
- **部署**：双镜像 v0.9.65；服务器端实测并发刷新 + 宽限命中

## v0.9.58 — 2026-10-26

### 加固：低危权衡收敛（4 项实施 + 2 项维持现状）

> 背景：v0.9.56/57 两轮审查登记了 6 项低危权衡，本轮按「最优解决方案」逐一收敛。

**实施的 4 项**

- **bcrypt cost 10 → 12 + 渐进重哈希**（[password.security.ts](/server/src/common/password.security.ts) 新模块）：新口令统一 cost 12（~250ms，GPU 破解成本显著抬升）；存量 cost 10 哈希在**登录成功时自动重哈希升级**（用户无感、无需迁移脚本、失败不阻塞登录）。同步修正 v0.9.57 的 DUMMY_HASH 为 cost 12——否则幽灵（10）与已升级用户（12）之间会出现新的 ~150ms 时差，侧信道换向复活
- **弱口令黑名单 + 语义规则**：注册/忘记密码重置/个人改密/管理员建号四个入口统一校验——60 个高频弱口令、包含用户名或邮箱前缀（≥4 字符）、键盘序列（qwerty 等）、≥4 连续同字符、≥4 位连续升/降序列（1234/abcd）。校验前置到邮箱验证码校验之前（弱口令直接打回，不让用户白白消耗一次性邮箱码）
- **保留用户名前缀**：`admin`/`root`/`system`/`official`/`staff`/`security` 等 21 个前缀开头（不区分大小写）的注册与建号一律 403，封堵 `admin_` 仿冒社工
- **e2e 回归**：新增弱口令 400、同源口令 400、保留名 403、渐进重哈希升级（getRounds 断言 10→12）、重置弱口令 400 共 5 用例；PASSWORD 常量换用非弱口令（原 `Abcd1234` 已入黑名单）；`NewPass5678` 因 5678 连续序列换用合规密码——93/93 全绿，单测 136 全绿

**维持现状的 2 项（重新评估后结论不变，理由固化）**

## v0.9.26 — 2026-10-10

### 可靠性专项（架构评审批次一）：prefork 连接池 fork 安全 + 解析任务对账与超时护栏 + 内部错误收口

> 背景：架构审计（17 项）后按「收益 × 依赖」排出的第一批——解决「现在就可能在发生的坏事情」：Celery prefork 子进程共享父进程连接池的随机故障、解析任务失败后永久卡死的无人对账、内部异常原文透传到前端。HTTPS/CSP 等「上公网前」项按既定决策暂缓。

- **连接池 fork 安全**（[db.py](/ai-service/app/db.py)）：
  - 根因：`ConnectionPool(open=True)` 在模块导入时建连，Celery prefork 主进程先 import 再 fork，池内 socket fd 被多个子进程继承共享——两进程并发操作同一连接导致协议错乱、随机失败，低并发下极难复现
  - 修复：`open=False` + 惰性开池 `_ensure_pool_open()`（fetch_all / fetch_one / execute 三入口各一行）；选惰性而非 `worker_process_init` 信号——该信号仅 prefork 池触发（solo/threads 不发），惰性对 API / prefork / solo 全部进程模型统一成立，子进程继承的只是 closed 状态，天然 fork-safe
  - `check=ConnectionPool.check_connection`：连接借出前探活，PG 重启后死连接自动丢弃重建（实测 restart postgres 后下个任务自愈）
- **并发 DDL 竞争修复（验证中暴露的新缺陷）**：prefork 双子进程并发首跑 `ensure_embedding_cache` 时，并发 `CREATE TABLE IF NOT EXISTS` 撞 Postgres 目录唯一约束（`pg_type_typname_nsp_index` UniqueViolation）导致任务无谓重试——`IF NOT EXISTS` 在并发下并不幂等。修复：事务级 advisory lock（`pg_advisory_xact_lock`）串行化 DDL。**这类潜伏问题只有连接池 fork 修复后才可能显现**
- **解析任务超时护栏**（[tasks.py](/ai-service/app/tasks.py)）：`task_soft_time_limit=1800` / `task_time_limit=2100`——扫描件 OCR 上限 20 页 × 单页 120s，理论最坏 40+ 分钟会堵死并发 2 的 worker 队列；`SoftTimeLimitExceeded` 单独捕获标 `failed`（超时是确定性失败，不进指数退避重试空转）。注：soft 限制仅 prefork 池生效，solo 池由硬限制兜底
- **卡死文档对账**（beat 周期任务）：
  - 心跳补齐：`set_doc_status()` 与完成更新补写 `updated_at=NOW()`——raw SQL 不触发 Prisma `@updatedAt`，此前无任何字段能判断「任务是否还活着」
  - 新增 `reconcile_stuck_documents`：`pending` 超 10 分钟（提交链路 fire-and-forget 丢失遗留）与 `parsing/indexing` 心跳超 40 分钟（worker 崩溃/强杀遗留）自动重置重投，单批上限 20 防故障恢复后惊群
  - 调度：worker 启动命令加 `-B`（beat 内嵌主进程，单实例标准做法，**不新增容器**），[docker-compose.yml](/docker-compose.yml) / [docker-compose.prod.yml](/docker-compose.prod.yml) 同步
  - 双跑防护：`chunks` 新增 `UNIQUE(doc_id, chunk_index)` 幂等索引（走 ensure_indexes 管理）+ 切片 INSERT 改 `ON CONFLICT DO NOTHING`——重投后与残留任务并发双跑退化为无害插入去重，而非脏数据
- **内部错误透传收口**（[internal.py](/ai-service/app/api/internal.py)）：新增 `safe_error_message()` 白名单——ValueError（业务层有意抛出的可读错误，如「ZHIPU_API_KEY 未配置」）保留原文，其余统一收敛为「AI 服务处理失败，请稍后重试」，完整堆栈只进服务端日志；`/chat` SSE 与 `/extract` 两处 except 接入，psycopg/SDK 细节不再随流透传到 BFF 与前端
- **踩坑记录**：
  1. **psycopg_pool 3.3 的 `open` 属性变成了方法**（3.2 是布尔）——状态判断必须用 `pool.closed`，且 `open(wait=False)` 由后台线程建连，DB 短暂不可用不阻塞任务进程（`wait=True` 会把首个任务卡在池启动上）

### 归因实验（四模式对照，20 条 golden QA × 4 = 80 次检索，prod 链路）

| 模式 | HitRate@5 | MRR@5 | 平均耗时 |
| --- | --- | --- | --- |

  - 边界说明：计数为进程内存存储，适配当前单实例部署；多实例横向扩容时需换 Redis 存储（throttler-storage-redis）

- **Nginx gzip 压缩 + 安全响应头**（`nginx/default.conf`，prod 为 bind mount，`nginx -s reload` 热生效）
  - gzip：`gzip_types` 覆盖 js/css/json/svg/xml，`min_length 1024`、`comp_level 5`、`vary on`——JS bundle 传输体积实测降约 70%；**刻意不含 `text/event-stream`**，SSE 流式问答不压缩，避免攒包影响打字机效果
  - 安全头：`X-Frame-Options: SAMEORIGIN`（刻意不用 DENY——文档预览 iframe 同源加载 `/api/v1/documents/:docId/file`，DENY 会打断预览）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`CSP frame-ancestors 'self'`；另 `server_tokens off` 隐藏版本号
  - 踩坑记录：nginx 的 `add_header` **不跨层继承**——`/assets/` location 一旦出现自己的 `add_header`，server 级安全头对其全部失效，必须在 location 内重复声明（已验证 `/assets/` 响应头齐全）
- 部署说明：以上 nginx 改动经 `docker exec nginx -t` 校验后 `nginx -s reload` 热加载即已生效，无需重建镜像

### 修复

- **Nginx 静态资源重复 Cache-Control 头**：`expires 30d` 指令会自动生成 `Cache-Control: max-age=2592000`，与手动 `add_header Cache-Control "public, immutable"` 叠加产生两条同名头；合并为单条 `add_header Cache-Control "public, max-age=2592000, immutable"`
- **统一异常过滤器 body.code 与 HTTP 状态码不一致**（`server/src/common/http-exception.filter.ts`）
  - 现象：冒烟测试发现 429 响应的 HTTP 状态正确，但响应体是 `{"code": 500, ...}`
  - 原因：`ThrottlerException` 的 `getResponse()` 是**字符串形式**，走过滤器的 string 分支，`code` 保持初始值 500 未被赋值；所有以字符串 message 构造的 `HttpException` 均受影响
  - 方案：进入 HttpException 分支时先令 `code = status`（对象形式响应仍可被 `r.code` 覆盖）；同时为 `code` 补显式 `number` 类型注解（TS 枚举字面量窄化导致赋值报错）
  - 验证：429 响应体为 `{"code": 429, "message": "操作过于频繁，请稍后再试", "data": null}`

### 修复

- **表格复制按钮从未渲染**（`frontend/src/utils/markdown.js`）
  - 现象：回答含表格，但页面无 `.table-block` / `.table-copy` 包裹，复制功能静默失效
  - 原因有两层：① wrapper 错误挂在 `md.renderer.rules.table`——markdown-it 渲染表格实际走 `table_open` / `table_close` 两个 token 规则键，`table` 键**永不被调用**，赋值静默无效；② 修正为 open/close 成对挂载后，本项目 markdown-it 版本对这两个键**没有默认渲染器**（值为 undefined），直接保存再调用抛 `TypeError: defaultTableOpen is not a function`
  - 方案：open 侧 fallback 到内置 `self.renderToken`，close 侧 fallback 空串
  - 教训：markdown-it 的 renderer 规则键必须按 token 类型核对（不能凭直觉猜键名），且不能假设默认渲染器一定存在——用 node 脚本以项目同款配置本地复现，是把"静默失效"变"显式报错"的定位利器

## v0.9.3 — 2026-10-05

### 新增

- **聊天页拖拽直接入库**（`frontend/src/views/ChatView.vue`）：文件拖入聊天页任意位置 → 全屏遮罩提示目标知识库（未选库时引导先选择）→ 按白名单（pdf/docx/txt/md/csv）与 20MB 上限过滤并逐条说明拒绝原因 → 入当前知识库并启动解析监听。拖拽入库与附件临时问答是两条独立路径，互不影响。技术要点：dragleave 抖动用进出计数器抵消；浏览器通知权限在 drop 用户手势内请求（符合 Notification API 的授权约束）。
- **文件夹批量导入**（知识库列表页「文件夹导入」按钮，`webkitdirectory`）：按 `webkitRelativePath` 首段目录名分组，同名知识库自动复用、缺库自动创建；隐藏文件 / 超限 / 非白名单文件跳过并汇总原因；每组 >10 个文件自动分批（对齐后端单次上限）；单组失败不阻塞后续组；完成后统一汇总通知并启动各库解析监听。
- **解析完成浏览器通知**（新增 `frontend/src/composables/useParseWatcher.js`）：5 秒轮询文档状态（单库最长监听 5 分钟自动停止），文档到达 `parsed` / `failed` 时发应用内通知（成功 5s / 失败 8s 存活）+ 浏览器系统通知（权限 denied 时静默降级）；同库重复监听自动合并目标、不叠加定时器；全部终态后自停。聊天页拖拽导入、文件夹导入、知识库详情页上传三条入口均已接入。

### 修复

- **知识库状态可能永久卡在「索引整理中」**（`ai-service/app/tasks.py`）
  - 现象：库内所有文档均已 `parsed`，但知识库状态停留在 `indexing`，导致聊天页知识库下拉（只列 ready 库）显示「无数据」
  - 原因：状态回写是"最后一次解析任务完成时打上 ready"，任何晚于它的状态写入（如删除/重建期间的并发更新）都会把库打回 `indexing`，且此后无任务再触发回写——乱序后永不自愈
  - 方案：任务完成时改为**按剩余工作量判定**——库内仍存在 `pending/parsing/indexing` 文档则保持现状，否则无条件归位 `ready`；每次任务完成都是一次自愈机会
  - 验证：重启 worker 后实测，任务消费成功且 KB 状态自动归位 `ready`，下拉接口恢复返回
- **通知可读性**：解析完成/失败通知存活时长 3s → 5s/8s（原 3 秒过短易被错过）
- **运维**：清理重复的 Celery worker（系统 Python 与 .venv 各一个，会竞争消费队列），统一以 `.venv` 单实例运行

### 测试

- 浏览器端到端（合成 DragEvent）：拖拽遮罩 → 入库 → 「导入成功」→「解析完成」通知全链路 PASS；文件夹导入按钮与 `webkitdirectory` 输入渲染 PASS；控制台无报错
- 任务链路：手动补投解析任务，worker 消费成功（切片 + 向量化 + 状态自愈）；测试产生的 6 个文档已通过 API 清理，知识库恢复 4 份真实文档

### 修复

- **全局响应拦截器误包装文件流**（`server/src/common/response.interceptor.ts`）
  - 现象：文件接口 HTTP 200、Content-Type 正确，但响应体是 `{code:0, data:{stream:...}}` 的 JSON 包装，前端拿到的是序列化对象而非原始内容
  - 原因：统一响应包装拦截器对所有 controller 返回值生效，`StreamableFile` 也被 `serializeBigInt` 转成普通对象再 JSON 序列化
  - 方案：拦截器对 `StreamableFile` 直通——流式/二进制响应必须绕过为 JSON 设计的包装层（与 SSE 绕过拦截器同理）
- **知识库详情「字段接缝」缺陷：文档列表空白但统计正常**（`frontend/src/api/knowledge.js`、`KnowledgeDetailView.vue`）
  - 现象：详情页统计行显示文档数 3，文档列表却始终「暂无文档」；配置 tab 保存检索参数后不生效

  - 教训：Mock 与真实后端的数据形状差异必须收敛在 API 接缝层，而不是散落在视图代码里
- **知识库状态卡在「索引构建中」**：3 份文档早已 `parsed`，KB 状态未回写（历史解析残留），一次性数据修复置为 `ready`
