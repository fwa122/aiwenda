## v0.9.30 — 2026-10-10

### 部署硬化专项（架构评审批次四）：非 root 运行 + 资源限额 + 日志轮转

> 背景：架构审计（17 项）批次四——剩余问题集中在容器部署硬化：3 个自建镜像均以 root 运行、全部服务无资源限制、容器日志默认无限增长。统计/重查询与同步路由并发两项经复核不属实或降级（trgm GIN 索引已建、FastAPI 同步路由走线程池不阻塞事件循环、MinIO 孤儿对象联动删除已实现），本轮不动。

- **非 root 运行**（[server/Dockerfile](/server/Dockerfile) / [ai-service/Dockerfile](/ai-service/Dockerfile) / [frontend/Dockerfile](/frontend/Dockerfile)）：
  - server 切自带 `node` 用户（uid 1000）：产物 `COPY --chown`，运行时无需写 `/app`（迁移写 DB、上传走 MinIO、临时文件走 /tmp）
  - ai-service 新建 `appuser`（uid 1000）：依赖装系统 site-packages（只读），worker 临时文件走 /tmp
  - frontend 换官方非 root 变体 `nginxinc/nginx-unprivileged:alpine`（uid 101、listen 8080、临时目录已指向 /tmp）——nginx 是公网入口，以 root 跑 master 是经典提权入口；[nginx/default.conf](/nginx/default.conf) 监听 80 → 8080，compose 映射 `${NGINX_PORT:-80}:8080`（宿主侧访问方式不变）
  - postgres/redis/minio 官方镜像进程本就以专用用户运行，不在本次范围
- **资源限额**（[docker-compose.yml](/docker-compose.yml) / [docker-compose.prod.yml](/docker-compose.prod.yml)，`deploy.resources.limits`）：nginx 256M/0.5cpu、server 512M/1.0、ai-service 1G/1.0、worker 1.5G/2.0（解析内存大头）、postgres 1G/2.0、minio 1G/1.0、redis 256M/0.5
- **Redis 内存策略**：`--maxmemory 200mb --maxmemory-policy noeviction`——broker 任务键无 TTL，eviction 会静默丢任务；noeviction 写满报错（任务提交失败可见）优于丢数据
- **日志轮转**（`x-logging` YAML anchor 复用）：7 个服务统一 `json-file max-size=10m max-file=3`——防长期运行撑爆宿主磁盘
- **补漂移**：双编排 ai-service 环境补 `FLASH_MODEL` 透传（v0.9.28 遗漏，此前容器内该配置不可覆盖）
- **实测**（Linux 全栈 smoke）：三镜像构建 ✓；全栈起齐 7 容器 healthy ✓；`docker inspect` 核对 User（nginx=101 / node=1000 / appuser=1000）与 LogConfig（7×max-size）与 Memory（512M/1G/1.5G）✓；非 root 下 entrypoint 迁移+种子 ✓；首页 200、admin 登录、JWT ver 签发全链路 ✓；`compose config` 双文件 ✓
- **升级须知**：① compose 编排已变，更新后需 `up -d --build`（或 prod 编排 `pull && up -d`）；② prod 免构建部署依赖重新发布的 `gujinyi666/aiwenda-*` 镜像（本地 `docker build` 后 push 覆盖）；③ smoke 验证发现 compose 不带 `--build` 会复用旧镜像缓存——更新编排后务必显式重建

## v0.9.27 — 2026-10-10

### 会话吊销专项（架构评审批次二）：tokenVersion 立即吊销——改密/封禁即刻踢下线

> 背景：架构审计 #2——改密只更新密码哈希、不清已签发令牌：凭据泄露后即使改密码，偷到的 refresh token 仍可续命 7 天（白名单只随登出/轮换删除）；封禁用户虽然 refresh 被状态检查拦下，但 access token 仍存活最长 2 小时。本版引入令牌版本号实现即时吊销，顺带把 jwt.strategy 从无状态校验升级为状态比对，修复两个附带旧问题。

- **schema + 迁移**（[schema.prisma](/server/prisma/schema.prisma) / [migrations/20261010120000_add_token_version](/server/prisma/migrations/20261010120000_add_token_version/migration.sql)）：`User.tokenVersion Int @default(0)`——存量用户默认 0，与老格式令牌平滑兼容，升级不掉线
- **签发携带 ver**（[auth.service.ts](/server/src/auth/auth.service.ts)）：login 与 refresh 轮换两处 access payload 均写入 `ver: tokenVersion`，refresh token 同样携带；refresh 端点在白名单校验之外比对 ver——旧 refresh 即使还在 7 天白名单窗口内也一并拒绝
- **校验升级**（[jwt.strategy.ts](/server/src/auth/jwt.strategy.ts)）：validate 从纯 payload 解析改为查库比对（主键点查），一箭三雕：
  1. `ver` 不等 → 401：改密/封禁自增版本号后，该用户**全部已签发令牌立即失效**（无需逐一清白名单，等效批量吊销）
  2. `status !== 'active'` → 401：封禁即时生效，消除「access 最长存活 2h」窗口
  3. 返回库内实时 role（此前返回 JWT 内的角色快照，改角色需等令牌过期才生效的旧问题一并修复）
  - 兼容：老格式令牌无 `ver` 字段按 0 处理（`payload.ver ?? 0`），历史令牌在版本号未变期间继续有效
- **触发点**（[user.service.ts](/server/src/user/user.service.ts)）：`changePassword` 自增（含 admin 侧）；`update` 在置 `disabled` 时自增；登出保持 jti 精确吊销不动版本号；解禁不回退版本——被禁用户旧令牌解禁后仍被拒，必须重新登录，防「解禁连坐复活旧会话」
- **踩坑记录**：
  1. **`prisma migrate dev` 会因库与迁移历史漂移要求 reset**——ai-service `ensure_indexes` 直接在库里建的索引（trgm GIN、唯一索引）不在任何迁移文件中，dev 库已被判漂移。本版改用手动迁移路径：手写 migration.sql → `prisma db execute` 应用 → `migrate resolve` 标记 → `prisma generate`，全程不触碰数据。**遗留**：漂移未基线化，后续 `migrate dev` 仍会触发 reset 询问，待专项整理（把 ensure_indexes 的 DDL 纳入迁移历史或反之）
  2. 测试基建顺带确认：global-setup 对测试库执行的是 `migrate deploy`（不做漂移检查），新迁移自动应用，测试链路零改动
- **测试**（[auth.e2e.spec.ts](/server/test/auth.e2e.spec.ts) 新增 4 例，用例顺序有讲究——legacy 兼容用例必须排在「不吊销」用例之后）：
  - 改密后旧 access 与旧 refresh 双双 401，新密码登录换发的新令牌可用
  - 管理员封禁后立即失效（status + ver 双防线）；解禁后旧令牌仍被拒
  - 管理员普通更新（未改状态）不吊销存量令牌
  - 测试 JWT_SECRET 现签无 `ver` 历史格式令牌 → 200（升级兼容性固化，防回归）
- **实测**：集成 19/19 ✓（含新迁移自动部署）、单元 17/17 ✓、`tsc` 构建通过 ✓
- **升级须知**：生产部署 `migrate deploy` 自动应用新迁移（纯加列带默认值，无锁风险）；jwt.strategy 每请求多一次主键点查（索引点查，量级无感）；全部在线用户**无需**重新登录

## v0.9.26 — 2026-10-10

### 可靠性专项（架构评审批次一）：prefork 连接池 fork 安全 + 解析任务对账与超时护栏 + 内部错误收口

> 背景：架构审计（17 项）后按「收益 × 依赖」排出的第一批——解决「现在就可能在发生的坏事情」：Celery prefork 子进程共享父进程连接池的随机故障、解析任务失败后永久卡死的无人对账、内部异常原文透传到前端。HTTPS/CSP 等「上公网前」项按既定决策暂缓。

- **连接池 fork 安全**（[db.py](/ai-service/app/db.py)）：
  - 根因：`ConnectionPool(open=True)` 在模块导入时建连，Celery prefork 主进程先 import 再 fork，池内 socket fd 被多个子进程继承共享——两进程并发操作同一连接导致协议错乱、随机失败，低并发下极难复现
  - 修复：`open=False` + 惰性开池 `_ensure_pool_open()`（fetch_all / fetch_one / execute 三入口各一行）；选惰性而非 `worker_process_init` 信号——该信号仅 prefork 池触发（solo/threads 不发），惰性对 API / prefork / solo 全部进程模型统一成立，子进程继承的只是 closed 状态，天然 fork-safe
  - `check=ConnectionPool.check_connection`：连接借出前探活，PG 重启后死连接自动丢弃重建（实测 restart postgres 后下个任务自愈）
- **并发 DDL 竞争修复（验证中暴露的新缺陷）**：prefork 双子进程并发首跑 `ensure_embedding_cache` 时，并发 `CREATE TABLE IF NOT EXISTS` 撞 Postgres 目录唯一约束（`pg_type_typname_nsp_index` UniqueViolation）导致任务无谓重试——`IF NOT EXISTS` 在并发下并不幂等。修复：事务级 advisory lock（`pg_advisory_xact_lock`）串行化 DDL。**这类潜伏问题只有连接池 fork 修复后才可能显现**
- **解析任务超时护栏**（[tasks.py](/ai-service/app/tasks.py)）：`task_soft_time_limit=1800` / `task_time_limit=2100`——扫描件 OCR 上限 20 页 × 单页 120s，理论最坏 40+ 分钟会堵死并发 2 的 worker 队列；`SoftTimeLimitExceeded` 单独捕获标 `failed`（超时是确定性失败，不进指数退避重试空转）。注：soft 限制仅 prefork 池生效，solo 池由硬限制兜底
- **卡死文档对账**（beat 周期任务）：
  - 心跳补齐：`set_doc_status()` 与完成更新补写 `updated_at=NOW()`——raw SQL 不触发 Prisma `@updatedAt`，此前无任何字段能判断「任务是否还活着」
  - 新增 `reconcile_stuck_documents`：`pending` 超 10 分钟（提交链路 fire-and-forget 丢失遗留）与 `parsing/indexing` 心跳超 40 分钟（worker 崩溃/强杀遗留）自动重置重投，单批上限 20 防故障恢复后惊群
  - 调度：worker 启动命令加 `-B`（beat 内嵌主进程，单实例标准做法，**不新增容器**），[docker-compose.yml](/docker-compose.yml) / [docker-compose.prod.yml](/docker-compose.prod.yml) 同步
  - 双跑防护：`chunks` 新增 `UNIQUE(doc_id, chunk_index)` 幂等索引（走 ensure_indexes 管理）+ 切片 INSERT 改 `ON CONFLICT DO NOTHING`——重投后与残留任务并发双跑退化为无害插入去重，而非脏数据
- **内部错误透传收口**（[internal.py](/ai-service/app/api/internal.py)）：新增 `safe_error_message()` 白名单——ValueError（业务层有意抛出的可读错误，如「ZHIPU_API_KEY 未配置」）保留原文，其余统一收敛为「AI 服务处理失败，请稍后重试」，完整堆栈只进服务端日志；`/chat` SSE 与 `/extract` 两处 except 接入，psycopg/SDK 细节不再随流透传到 BFF 与前端
- **踩坑记录**：
  1. **psycopg_pool 3.3 的 `open` 属性变成了方法**（3.2 是布尔）——状态判断必须用 `pool.closed`，且 `open(wait=False)` 由后台线程建连，DB 短暂不可用不阻塞任务进程（`wait=True` 会把首个任务卡在池启动上）
  2. **Windows 宿主机 Celery 不支持 prefork**，fork 修复无法在本地 dev 模式 e2e 验证——本版验证全部在 Linux 容器（挂 dev 基础设施网络）完成
  3. 容器内 `python /tmp/x.py` 的 `sys.path[0]` 是脚本目录而非 WORKDIR，`-w /app` 不够，需显式 `PYTHONPATH=/app`
- **实测**（Linux 临时容器，prefork×2 + dev 基础设施）：双子进程并发解析零 psycopg 协议错误 ✓；DDL 加锁后 UniqueViolation 不再出现 ✓；PG 重启后重投解析自愈 ✓；手工构造两类卡死文档 → beat 5 分钟周期内自动重投并全部恢复 `parsed`、切片数精确无重复 ✓；停 PG 触发内部异常 → SSE 仅透出通用文案、堆栈留服务端日志 ✓
- **升级须知**：ai-service 镜像需重新发版；worker 必须带 `-B` 才有对账能力；存量 chunks 若已有重复数据，唯一索引创建失败仅打警告不阻塞启动（沿索引容错惯例），可人工清重后重启补建

> 背景：此前 access token 2h 硬过期且无续期手段，用户每 2 小时被强制重登；token 泄露后 2h 内全程有效无救济手段。

  - `POST /auth/logout`：吊销 refresh token（access token 存活至自然过期，风险窗口 ≤2h）

## v0.9.9 — 2026-10-06

### 修复（检索架构）

- **Rerank 与 hybrid 混合召回解耦**（`ai-service/app/retrieval.py`）
  - 原实现 `use_fusion = bool(hybrid or rerank)`：开精排会**隐式启用**「词法召回 + RRF 融合」，导致 ① 评测关/开对比混杂了召回通道差异；② pg_trgm 词法在中文长文本上的噪声候选挤占/降位正确切片
  - 改为 `use_fusion = bool(hybrid)`：rerank 只对「当前模式的候选」交叉重排（纯向量模式 → 向量候选；融合模式 → RRF 候选），两者可独立开关
  - rerank 请求显式传 `top_n = len(rows)`，防 API 默认截短候选
  - 行为变化：知识库配置 `rerank=true` 时由「hybrid+rerank」变为「向量+rerank」；需要组合者显式同时开启 hybrid
- 起因：v0.9.8 评测显示「精排开」HitRate 90% / MRR 0.586 对比基线 100% / 0.691 净负优化，四模式归因实验定位主因为召回通道耦合（见下）

### 归因实验（四模式对照，20 条 golden QA × 4 = 80 次检索，prod 链路）

| 模式 | HitRate@5 | MRR@5 | 平均耗时 |
| --- | --- | --- | --- |
| ① 纯向量（基线 = 精排关） | **100%** | **0.691** | 405ms |
| ② 向量+rerank（解耦后新「精排开」） | 90% | 0.655 | 中位 ~750ms（均值 1212ms 被单次 10.5s API 抖动拉高） |
| ③ 仅混合召回（隔离召回通道） | 85% | 0.574 | 314ms |
| ④ 混合+rerank（旧版耦合「精排开」） | 90% | 0.576 | 815ms |

- **负提升归因定论**：
  1. **主犯（−0.117）**：召回通道耦合——③ 证明单独换掉召回通道就足以从 0.691 掉到 0.574；词法路的 `word_similarity` 对中文长文本噪声大，q03/q14/q19 在纯混合模式下直接跌出 Top5
  2. **次因（−0.036）**：精排模型本身在「QA 与文档同源」的数据上收益有限，②中 q03/q14 被重排挤出 Top5
  3. **实锤**：④（0.576）与 ③（0.574）几乎一致——旧评测的「精排开」数字几乎全由召回通道贡献，精排模型本身在融合候选上近乎中性（0.574→0.576）
- **解耦收益**：「精排开」MRR 0.576 → 0.655（+0.08），HitRate 持平 90%；精排仍不及纯向量基线 → **维持默认精排关**的决策不变，精排保留为措辞差异大场景的可选项
- 口径互验：④ 与 v0.9.8 浏览器评测 UI 的数字一致（90% / 0.576 vs 90% / 0.586，运行间正常波动），证明脚本口径与 UI 相同

  - 全局兜底：单 IP 每分钟 300 次（`server/src/app.module.ts` `ThrottlerModule.forRoot` + `APP_GUARD` 注册全局 `ThrottlerGuard`，注册顺序在 `JwtAuthGuard` 之前 → 登录/注册等公开接口同样受保护）
  - 高成本接口单独收紧（`@Throttle` 覆盖默认值）：`POST /chat/completions` 15 次/分（LLM token 消耗，全系统最高成本）、`POST /chat/attachments` 20 次/分、`POST /chat/suggestions` 30 次/分（glm-4-flash 调用）、`POST /auth/login` 10 次/分（按 IP 抬高密码爆破成本）、`POST /auth/register` 5 次/分、文档上传与重解析各 10 次/分（解析+切片+embedding 计算成本高）
  - `server/src/main.ts` 设置 `trust proxy = 1`：nginx 已传 `X-Forwarded-For`，`req.ip` 取真实客户端 IP——不设置的话所有用户共享 127.0.0.1 一个桶，限流会整体误伤
  - 边界说明：计数为进程内存存储，适配当前单实例部署；多实例横向扩容时需换 Redis 存储（throttler-storage-redis）
- **前端 SSE 限流反馈**（`frontend/src/api/chat.js`）：`streamAnswer` 在读流前检查 `res.ok`，非 2xx 时解析 JSON 的 message 抛给 `onError`——此前 429 返回的 JSON 会被当 SSE 流读取，因无 `data:` 行而静默结束，界面卡住无任何反馈
- **Nginx gzip 压缩 + 安全响应头**（`nginx/default.conf`，prod 为 bind mount，`nginx -s reload` 热生效）
  - gzip：`gzip_types` 覆盖 js/css/json/svg/xml，`min_length 1024`、`comp_level 5`、`vary on`——JS bundle 传输体积实测降约 70%；**刻意不含 `text/event-stream`**，SSE 流式问答不压缩，避免攒包影响打字机效果
  - 安全头：`X-Frame-Options: SAMEORIGIN`（刻意不用 DENY——文档预览 iframe 同源加载 `/api/v1/documents/:docId/file`，DENY 会打断预览）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`CSP frame-ancestors 'self'`；另 `server_tokens off` 隐藏版本号
  - 踩坑记录：nginx 的 `add_header` **不跨层继承**——`/assets/` location 一旦出现自己的 `add_header`，server 级安全头对其全部失效，必须在 location 内重复声明（已验证 `/assets/` 响应头齐全）
- 部署说明：以上 nginx 改动经 `docker exec nginx -t` 校验后 `nginx -s reload` 热加载即已生效，无需重建镜像

### 修复

- **Nginx 静态资源重复 Cache-Control 头**：`expires 30d` 指令会自动生成 `Cache-Control: max-age=2592000`，与手动 `add_header Cache-Control "public, immutable"` 叠加产生两条同名头；合并为单条 `add_header Cache-Control "public, max-age=2592000, immutable"`
- **统一异常过滤器 body.code 与 HTTP 状态码不一致**（`server/src/common/http-exception.filter.ts`）
  - 现象：冒烟测试发现 429 响应的 HTTP 状态正确，但响应体是 `{"code": 500, ...}`
  - 原因：`ThrottlerException` 的 `getResponse()` 是**字符串形式**，走过滤器的 string 分支，`code` 保持初始值 500 未被赋值；所有以字符串 message 构造的 `HttpException` 均受影响
  - 方案：进入 HttpException 分支时先令 `code = status`（对象形式响应仍可被 `r.code` 覆盖）；同时为 `code` 补显式 `number` 类型注解（TS 枚举字面量窄化导致赋值报错）
  - 验证：429 响应体为 `{"code": 429, "message": "操作过于频繁，请稍后再试", "data": null}`

  - 教训：Mock 与真实后端的数据形状差异必须收敛在 API 接缝层，而不是散落在视图代码里
- **知识库状态卡在「索引构建中」**：3 份文档早已 `parsed`，KB 状态未回写（历史解析残留），一次性数据修复置为 `ready`

  - 现象：上传中文命名的文件后，列表中文件名显示为 `Ã¨Â°…` 形式乱码（如「许昌学院2026年…」变成 `è®¸æå­¦é¢2026å¹´…`）

### 修复

- **聊天输入框「检索设置」按钮点击无反应**（`frontend/src/components/ChatInput.vue`）
  - 现象：点击按钮后设置弹层（TopK / 相似度阈值 / 混合检索开关）不出现，无任何反馈
  - 原因：`el-popover` 的 `#reference` 槽内嵌套了 `el-tooltip`（组件）。Element Plus 要求该槽为真实 DOM 元素，嵌套组件导致弹层触发器绑到"非元素根节点"，弹层节点虽挂载但恒为 `display: none`；控制台伴随警告 `Runtime directive used on component with non-element root node`
  - 方案：改用官方 virtual-ref 模式——popover 通过 `:virtual-ref` 绑定按钮引用，tooltip 独立包裹同一按钮，两者解耦嵌套
