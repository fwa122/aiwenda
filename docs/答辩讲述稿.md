## 一、开场与背景（约 30 秒）

各位老师好，我演示的作品是「AI 知识库问答系统」。

做它的动机很直接：企业文档散落在各个地方，查资料靠翻文件；直接问大模型，它不知道企业内部知识，还会一本正经地编。所以我基于 RAG——检索增强生成——做了一套完整系统：用户上传企业文档，系统自动完成解析、切片、向量化，之后就能用自然语言提问，拿到**带引用编号、可定位到原文页码**的回答。

整个项目的前端、后端、AI 服务和部署全部独立完成，支持一键 Docker 部署。

## 二、整体架构（约 40 秒）

架构上是 6 个容器、三层分工：

- 前端 Vue 3 + Pinia，由 nginx 托管并反向代理；
- 中间是 NestJS 的 BFF 层，负责 JWT 鉴权、权限模型、业务数据，以及 SSE 流式编排；
- 最里层是 Python FastAPI + Celery 的 AI 服务，专管计算密集的工作：文档解析、切片、向量化、检索与生成。耗时的解析任务丢给 Celery worker 异步执行，用 Redis 队列解耦。

数据只用一个 PostgreSQL：业务表和 pgvector 向量放在同一个库里，向量建 HNSW 索引加速近邻检索。**这样拆的好处是：BFF 管"业务正确"，AI 服务管"算法效果"，两边用内部令牌通信，各自独立演进和扩容。**

## 三、三个技术亮点（约 70 秒）

**亮点一：混合检索内核。** 纯向量检索对专有名词、文件编号这类"字面匹配"不敏感，所以我做了双路召回：向量一路、pg_trgm 词法一路，各自独立取 Top-N 求并集，再用 RRF 倒数排名融合（k=60），最后过一道 rerank 模型做交叉精排。**每一环失败都有降级路径**——rerank 挂了回退 RRF 排序、词法扩展不可用就在候选池内兜底——保证检索永远有结果。多轮对话还会先做查询改写，把"那它多少钱"这种指代问题消解成完整查询再去检索。

**亮点二：文档处理流水线。** PDF 用标题启发式还原文档结构，表格转成 Markdown，扫描件走 OCR 兜底；切片按标题层级切，并把标题注入切片首行，让向量携带章节上下文，再合并相邻小段，避免语义被切碎。

**亮点三：防幻觉与可溯源。** 三道防线：第一，检索为空时根本不调大模型，直接返回兜底话术；第二，上下文按字符预算截断、编号引用，系统提示词强制标注 [n]；第三，生成后再校验一遍，回答里没有 [n] 就自动补参考来源。**用户点击引用编号能直接定位到原文片段和页码——这是"可信"的关键。**

## 四、现场演示（约 30 秒）

（切浏览器）部署就是一条 `docker compose up -d`。我演示三个环节：

1. 新建知识库、上传一份 PDF，能看到解析进度和失败原因；
2. 先在「检索测试」页调 Top-K、打开混合检索和 Rerank，直观对比召回差异；
3. 然后正式提问——注意回答是流式输出的，点引用编号直接跳到原文定位；最后把会话切换到另一个模型再问一次，模型选择随会话持久化。

## 五、收获与规划（约 20 秒）

这个项目我最大的收获，是完整走通了"从文档到可信回答"的全链路工程，并且做了一轮安全专项加固：修复 IDOR 越权、内部接口 fail-closed 鉴权、上传白名单、XSS 防护。也踩了很多真实的坑，比如 nginx 必须关 SSE 缓冲、Moonshot 流式要显式关闭 thinking 参数。后续我计划接入 MinIO 对象存储、补充限流和检索效果评估闭环。

## 附一：关键数字卡（防追问，讲前扫一眼）

| 数字/事实 | 出处与说明 |
| --- | --- |
| 6 容器 / 11 张表 | nginx、server、ai-service、worker、postgres、redis；Prisma schema |
| embedding-3，1024 维，HNSW 索引 | 智谱向量模型；`pgvector` 近邻索引 |
| 向量阈值默认 0.28 | `retrieval.py search()` 参数，知识库可配 |
| 候选池 = max(topK×4, 30) | 双路各取的 Top-N 大小 |
| RRF k=60 | 融合公式 Σ 1/(k+rank)，只看排名不看原始分，规避两路分数量纲不可比 |
| 词法准入 0.2 / word_similarity 阈值 0.1 | 融合模式下低向量分切片的保留条件；阈值放宽是因短查询对长文本 |
| 上传 ≤20MB 白名单；附件 ≤5MB | 文档入库与临时附件两条限制 |
| SSE 事件序列 | `references → delta… → done`（done 带 model/elapsedMs/tokens/rewrittenQuery） |
| Moonshot：temperature=0.6、thinking=disabled | 平台强约束与流式必要参数 |

## 附二：高频追问 → 应答要点

| 追问 | 一句话应答（展开见对应文件） |
| --- | --- |
| 为什么 BFF 和 AI 服务分开？ | 职责分离（业务正确 vs 算法效果）；Python 的 AI 生态；解析重活异步化互不阻塞；内部令牌 fail-closed（`ai-service.client.ts`） |
| 为什么 pgvector 不用 Milvus？ | 当前量级下单库搞定业务+向量，事务一致、免额外运维；HNSW 够用（`后端开发方案.md` 选型分析） |
| 为什么 SSE 不用 WebSocket？ | 回答是单向流，SSE 走普通 HTTP、反代简单、自动重连语义简单（`sse.writer.ts`） |
| 切片太大/太小的问题？ | 太大语义稀释、检索不准；太小上下文碎片化、引用碎。用标题层级 + heading 注入 + 相邻合并缓解（`chunker.py`） |
| 检索质量怎么评估？ | 检索测试页可实时调 Top-K/阈值/混合/Rerank 做对比；规划中做答案评价闭环（`knowledge-base` 检索测试接口） |
| 检索不到怎么办？ | 不调 LLM 直接兜底话术；有附件时用附件作答（`internal.py` chat） |
| 引用编号会不会指向错来源？ | 附件不占编号，避免悬空 [n]；生成后校验无 [n] 自动补来源列表（`internal.py`） |
| 安全做了什么？ | IDOR、fail-closed 内部令牌、上传白名单+路径穿越防护、CORS 白名单、JWT 强密钥校验、DOMPurify 防 XSS（`安全修复总结报告.md`） |
| 失败容错怎么设计？ | 逐级降级：rerank 回退 RRF、词法降级池内兜底、改写失败用原问题、解析任务重试+失败原因展示 |
| 为什么模型按前缀路由？ | `glm-*`→智谱、`kimi-*`→Moonshot 的注册表模式，新增 Provider 只注册不改调用方（`llm.py`） |

## 附三：排练提示

- **演示用预置数据**：提前建好一个已解析完成的知识库，现场只上传一份小文档，避免 OCR/解析等待卡壳。
- **网络预案**：提前录一段演示视频备用；LLM API 万一超时，讲检索测试页照样能撑住场面（它不依赖大模型生成）。
- **打断应对**：评委中途插问先答结论再给依据，答完回到演示主线，别被带丢节奏。
- **计时**：正文讲 3 分半内；彩排时录音回听，重点检查「亮点」段是否讲顺。
